# Diecastly — Decision Log

Concise record of approved decisions. Newest decisions appear at the end.

| # | Decision | Rationale |
|---|---|---|
| D1 | **Single Next.js application** with `/admin` and storefront route groups | One deployable unit; no duplicated types/auth/config |
| D2 | **Supabase as the entire backend** (Postgres, Auth, Storage) | No separate API server; minimal operational surface |
| D3 | **Postgres RPCs for atomic business operations** | Guarantees inventory/order/payment consistency; overselling impossible |
| D4 | **Metadata writes use RLS directly; financial/stock writes use RPC only** | Keeps the RPC layer small and focused |
| D5 | **Separate `inventory_stock` table** from `products` | Metadata edits can never touch stock; stock writes denyable at RLS |
| D6 | **Append-only `inventory_movements` ledger** | Reliable audit trail; current stock alone is insufficient |
| D7 | **Inventory movement reference contract** enforced by CHECK | RPCs must set `reference_type`/`reference_id` consistently |
| D8 | **Stock changes use conditional atomic updates** (`quantity >= qty`) | Prevents overselling and negative inventory under concurrency |
| D9 | **Multi-item stock decrements ordered by product id** | Avoids deadlocks |
| D10 | **Token-based guest order access** (`orders.access_token`, 122-bit) | Customers cannot access another order by guessing number/phone |
| D11 | **Phone/email link orders to customers but never authenticate** | Identity for history without treating contact data as a credential |
| D12 | **Guest checkout; no customer accounts** | Lowest friction for occasional buyers |
| D13 | **Manual payments in v1** (cash, manually verified UPI, COD) | Matches how the business actually operates |
| D14 | **Gateway-ready payment schema** (`provider`, `provider_payment_id`, unique idempotency index) | Online provider can be added later without redesign |
| D15 | **`payment_events` deferred** to the gateway phase | Not needed in v1; avoids unused infrastructure |
| D16 | **`payments` is the single source of truth; payment state derived-only** | No second mutable payment state to drift |
| D17 | **No stored `orders.amount_paid` or `orders.payment_status`** | Derived in `v_order_financials` |
| D18 | **`orders.expires_at` for unpaid/pending online orders** | Marks stock holds; duration from settings |
| D19 | **No background expiry job in v1** | Phase 2; manual/admin-driven for now |
| D20 | **Expiry must reuse `cancel_order`** | One authoritative cancel/restock path |
| D21 | **`payment_status` derived-only; filters via `v_order_financials`** | Single source of truth over filter convenience |
| D22 | **Fulfillment status and payment status are independent** | In-person sale is fulfilled at recording, paid state separate |
| D23 | **In-person sale reversal window** (`settings.in_person_reversal_window_hours`, default 24) | Completed sales are not arbitrarily reversible later |
| D24 | **In-person reversal is a cancellation+reversal, not a return** | Simplest correct model; returns deferred |
| D25 | **Out-of-window returns handled manually** (`adjust_stock(return)` + `refund_payment`) | No returns system in v1 |
| D26 | **Snapshot historical product/price/cost data on order lines** | Later edits never rewrite historical profit |
| D27 | **Canonical profit model** with no double-counted discounts | Every report uses one definition |
| D28 | **Product archival, never hard deletion** | Preserves order history through snapshots |
| D29 | **Admin is desktop-first; storefront is mobile-first** | Matches actual usage |
| D30 | **Single seeded admin, but `admin_users` supports many** | No schema redesign when a helper is added |
| D31 | **`orders`/`order_items`/`order_status_history` are RPC-write-only** | Stored totals cannot be hand-edited |
| D32 | **IST used for reporting day boundaries** | Local business timezone |
| D33 | **Payments never mutate fulfillment status** | `record_payment`/`refund_payment` only touch the ledger; recording full payment does not confirm an order; fulfillment changes only via order-status RPCs |
| D34 | **POS `unit_price` must be > 0 in v1** | No zero-value lines; enforced in Zod and in a DB CHECK |
| D35 | **In-person reversal window enforced server-side in the RPC** | The UI only surfaces eligibility; the authoritative timestamp check is in `cancel_order` |
| D36 | **Opening stock initialized at most once per product** | Partial unique index on `initial` movements; `set_initial_stock` is idempotent on retry |
| D37 | **Server-side idempotency** | Same key reuses the original successful result; a different payment reusing a provider payment id is rejected; never UI-only |
| D38 | **v1 is single-business, single-location, single-admin** | No tenant/workspace/organization abstractions; multi-tenant deferred until actually required |
| D39 | **The till records only the applied amount** (`min(received, total)`); cash change due is shown but never recorded | The payments ledger holds money applied to the order, not tender; change is a counter detail, not revenue |
| D40 | **Online prices come from the catalog, never the caller** | `place_online_order` is `security definer` and granted to `anon`, so a supplied unit price or line discount would be the customer's to choose. The POS keeps its price override: that caller is an authenticated admin entitled to negotiate at the till. The two channels differ on purpose |
| D41 | **A sale with no payments records no payment** | Absent and empty payment lists both mean "nothing was collected", so both create zero payment rows and derive `unpaid`. The order is still `completed` and stock is still decremented — fulfilment and payment stay independent. A sale on credit is then settleable through the normal payment path |
| D42 | **A recorded payment may not exceed the outstanding balance** | Because payment state is derived, an overpayment raised nothing: it produced a negative balance that every surface hid, so a mistyped digit booked a surplus nothing revealed. Mirrors the cap `refund_payment` already had. The idempotency check runs first, so a retry still returns the original result |
| D43 | **The canonical subtotal is the exact sum of the line totals** | Both sale functions accumulate into unconstrained numerics and round once at the end, rather than rounding a `numeric(12,2)` running total at every step. Rounding a running sum and summing rounded parts are different operations, so the documented identity is now structural rather than incidental |
| D44 | **A product with images always has a primary image** | The schema guarantees *at most* one primary; deletion could leave *none*, and the placeholder fallback meant nothing surfaced it. Deleting the primary promotes the next image by display order in the same operation |
| D45 | **An out-of-range page is a distinct list state** | Telling the admin a populated catalog was empty invited a duplicate product. One shared decision distinguishes error / out-of-range / no-matches / empty / rows, and pagination renders whenever a total is known, not only when the page has rows |
| D46 | **List filter values are validated, not cast** | A type assertion has no runtime effect, so `?stock=bogus` silently became "out of stock" and an unknown movement type errored the page while the control read "All movements". Values are validated against the same enumerations the controls render from, and an unrecognised value is treated as absent rather than substituted |
| D47 | **Three `product_images` mutations are security-definer RPCs, not direct table writes** | `product_images` is metadata and D4 otherwise keeps metadata on the RLS lane. These three are a deliberate exception taken for **atomicity**, not encapsulation. Each was a sequence of independent client statements and each could be interrupted into a broken state: set-primary left the product with *no* primary if the second write failed; reorder left the order half-applied while reporting failure; and delete promoted the successor *before* removing the old primary, which the partial unique index forbids outright, so deleting a primary image silently did nothing |
| D48 | **A product with images has exactly one primary image, and the two facts are made true together** | The partial unique index guarantees *at most* one primary, which on its own permits *none* — the state that made the storefront fall back to the placeholder for every thumbnail. Three paths are therefore each closed by one transaction: a `BEFORE INSERT` trigger makes a product's first image its primary; `delete_product_image` removes the old primary and promotes its successor together; and `set_primary_image` is deliberately two statements inside one transaction, because a single `UPDATE` would depend on the order rows are visited in — the unique index is checked per row. **Limit, stated rather than implied:** the admin-all RLS policy still permits a direct `UPDATE ... SET is_primary = false` that would orphan a product. No application code issues one, so the guarantee holds over the paths the application uses, not over arbitrary SQL. That is the price of leaving `product_images` on the metadata lane |
| D49 | **Expected failures keep a single `P0001` and are distinguished by message text** | Distinct SQLSTATEs were measured, not assumed: custom codes are accepted and catchable by name on PostgreSQL 18, but a custom code is **no longer caught by `exception when sqlstate 'P0001'`**, and 7 existing test assertions pin the expected SQLSTATE. The user-visible defect this would have addressed was already fixed by mapping all 24 codes to friendly messages, so this would be a public-contract change with no remaining user benefit. `security.md` is corrected to describe the actual design |

| D50 | ****An idempotency key denotes exactly one request, and a replay must be proven to be the same request**** | `place_online_order` replayed on any matching key and returned that order's `access_token` — the sole credential for reading an order (§6 of `security.md`, D10) — so two buyers sharing a key meant the second received the first's token and their own order was never created. A replay is now allowed only when the stored order matches the incoming request on channel, payment method, customer phone and the summed per-product line quantities; anything else raises `idempotency_conflict`, which is what `record_payment` already did. **No new column:** the order already stores all of that, so "is this the same request?" is answerable from the row itself, and an order written before this change still compares correctly. Quantities are summed per product before comparison, so re-splitting the same quantities across lines is still a retry. The shipping address is deliberately *not* compared — it is the one field a re-rendered checkout form might present differently, and a false conflict on a genuine retry is worse than the marginal disclosure risk |
| D51 | ****The storefront links to a customer record but never modifies one**** | `place_online_order` is `security definer` and granted to `anon`, so its `on conflict do update` bypassed the RLS that makes `customers` admin-only, and any anonymous caller could rewrite the stored name and email of any customer whose phone number they could guess — verified: an existing row's name became `ATTACKER`. The upsert existed only to obtain an id for `orders.customer_id`, so it is now insert-then-reselect on conflict, which links without mutating and without bumping `updated_at` on a repeat order. Nothing is lost: the order snapshots name and email at write time, and editing a customer is the admin metadata lane's job. `record_in_person_sale` keeps its upsert, because that caller *is* an admin entering the customer |
| D52 | ****A recorded payment means money received and kept, so the POS cap belongs on the server**** | `record_payment` was capped in D42; `record_in_person_sale` was not, so it accepted more than the order total and produced `balance = -4900.00` with a derived status of `paid` — a negative balance every consumer hid, the receipt clamping it to zero. Cash tendered over the total is a normal till event, so the alternative (recording the tendered amount and treating the difference as change) was considered and rejected: it would change what `net_paid` means and force every report to subtract change. The POS already sends the amount *retained* — `applied = Math.min(receivedValue, total)`, with change displayed separately — so the clamp was simply UI-only, which `security.md` §5 forbids. Adding it server-side changes no money definition; it makes the existing intended behaviour authoritative |
| D53 | ****The shared validation layer may not be looser than the column it feeds**** | Three schemas accepted values the database rejects: an unbounded POS `lineDiscount` that `invalid_discount` refuses, a `moneyField` with no ceiling that overflowed `numeric(12,2)`, and two independent definitions of `low_stock_threshold` with different bounds — so the product form accepted a value the inventory dialog refused, and neither matched int4. All three now enforce the column's rule, and a column has exactly one definition (`lowStockThresholdSchema` is re-exported, not copied). Two are bounded by the *storage* limit and one by a business ceiling of 100,000; where a business ceiling was chosen it is because a storage-limit message is not useful to an admin. The general rule is pinned by a test that walks a shared set of boundary values through both schemas and fails if they disagree, so this class cannot return silently |
| D54 | ****The expected-failure lookup matches the longest token, and an exact match first**** | `describeDbError` returned the first token found as a substring, scanning in declaration order, and `invalid_payment` is a prefix of `invalid_payment_method` four entries above it — so a rejected payment method was reported as "Enter an amount greater than zero." That is worse than a generic message, because a specific-but-wrong one sends debugging down the wrong path. Lookup is now exact-then-longest, which makes the order of the table irrelevant, so the next code added cannot reintroduce it. A test now asserts every raised code maps to a message distinct from every other's, which catches any future collapse |
| D55 | ****A hand-written remedy uses `failWith`; only database errors go through `fail`**** | `fail` is `describeDbError`, which recognises SQLSTATEs, constraint names and mapped tokens. A plain `{ message }` matched none of them, so `uniqueSlug`'s message — the one in the codebase written specifically to name a remedy, "set one explicitly" — was replaced by the generic fallback and no admin ever saw it. `failWith` exists for failures the application has already diagnosed. It is deliberately narrow: the accompanying test pins that `fail` still translates a real database error, so it cannot become a way to skip translation |

## Rejected findings

Two candidate defects were investigated during the audit and **disproven**. Both are recorded so they are not re-raised, because each looks plausible and each was reported by a review pass that could not execute SQL.

| Finding | Why it was raised | Why it is wrong |
| --- | --- | --- |
| `v_low_stock` would fail with a permission error for an admin | `v_low_stock` is a `security_invoker` view selecting another `security_invoker` view, and the PostgreSQL `CREATE VIEW` documentation states that invoker permission checks *are* propagated through a nested security-invoker view | The concern is structurally sound, but `v_product_stock` **is** in the grant list. The grant is correct and there is no bug. Do not "fix" the grants |
| Primary product images always render as a placeholder | Every thumbnail fell back to the placeholder image | The view's correlated subquery is correct. The real defect was that deleting the primary image left no row *marked* primary — a different cause with a different fix, now closed by D48. Do not touch the view |
